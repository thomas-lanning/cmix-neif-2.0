# Hutter Prize rules for the cmix-neif fork

Reviewed 17 November 2026. The official detailed rules govern eligibility. The prize homepage lists awarded records. Matt Mahoney's benchmark and entrants' reports can reveal earlier submissions that could raise the bar. Record the date and recheck all three before submitting. [Rules](https://www.hutter1.net/prize/hrules.htm) · [Awarded records](https://www.hutter1.net/prize/) · [Large Text Compression Benchmark](https://mattmahoney.net/dc/text.html#cmix-neif)

## What a candidate must produce

- Use the exact 1,000,000,000-byte `enwik9`. Its SHA-256 is `159b85351e5f76e60cbe32e04c677847a9ecba3adc79addab6f4c6c7aa3744bc`. The native x86 Linux or Windows compressor must turn that input into an archive. Our self-extracting archive must reproduce the original bytes when run alone, with no arguments or outside data. Verify the decoded output against the reference in a fresh directory. [Corpus](https://mattmahoney.net/dc/textdata.html) · [Reference digest](https://github.com/marwoelk/cmix-neif-2.0#11-prerequisites) · [Rules](https://www.hutter1.net/prize/hrules.htm)
- For this packaging, score the actual compressor file, the entire generated self-extracting archive and any required execution or compilation options. The decoder, weights, tables, dictionaries and code inside those artifacts already contribute to their file sizes. In the upstream layout the packed transformer is embedded once in each executable. A 1-byte reduction in that container saves 2 score bytes if everything else holds constant. Do not add that penalty again when scoring complete artifacts. [Rules and relaxations](https://www.hutter1.net/prize/hrules.htm) · [Upstream packaging](https://github.com/marwoelk/cmix-neif-2.0#result)
- The optional separate-decoder format charges compressor + archive data + **twice** the separately supplied decoder, plus required options. If the compressor and decoder are byte-identical the decoder multiplier falls to one. The rules also allow certain zipped-source-and-makefile submissions. The project's ordinary source tarball accompanies the executable for rebuilding and review. Its size does not replace the executable size in our chosen format. [Rules and relaxations](https://www.hutter1.net/prize/hrules.htm) · [FAQ on equivalent alternatives](https://www.hutter1.net/prize/hfaq.htm)
- Benchmark-specific tuning and training on `enwik9` are allowed. Offline GPU training is compatible with the published FAQ and the 2026 prize-winning transformer precedent. Every piece of learned information needed at execution must be supplied by counted artifacts or derived from permitted inputs during the run. Scored executables operate offline without extra installations, external weights, external dictionaries or hidden data. Standard system-library use is allowed. [Rules](https://www.hutter1.net/prize/hrules.htm) · [FAQ on batch training, pretrained models and compute](https://www.hutter1.net/prize/hfaq.htm)

## Limits and test conditions

Both compression and decompression run on one CPU core with no GPU. Each invocation has a strict wall-time limit of `70,000 / T` hours for the evaluating host's Geekbench **5 single-core** score `T`. At `T = 1,284` this gives about 54.52 hours per invocation. The current detailed formula takes precedence over older illustrative time budgets in the FAQ. Limits apply to both programs, including preprocessing, unpacking and postprocessing. The official text specifies at most 10 GB of RAM and 100 GB of temporary storage. [Official overview](https://www.hutter1.net/prize/) · [Detailed resource rule](https://www.hutter1.net/prize/hrules.htm)

The Linux Judging Assistant reviewed here is commit `4f4a9a1a14abdbae6522ab06b4b898cfdfd0071b`. It enforces **10 GiB of resident memory** as the greater of the per-process maximum and sampled aggregate RSS of concurrently running descendants. It separately records cgroup usage including filesystem cache. It allows **100,000,000,000 bytes** of temporary disk and uses a 16 GiB execution environment with swap disabled. Its host requires x86-64 Linux, at least 16 GiB RAM for serial runs, supported kernel/container confinement, and at least 100 GB free work storage in addition to inputs, images and retained results. The ordinary run calibrates Geekbench and verifies cold input caches. These details describe this verifier revision. [Pinned verifier and resource accounting](https://github.com/jabowery/HutterPrizeJudgingAssistant/blob/4f4a9a1a14abdbae6522ab06b4b898cfdfd0071b/README.md)

Use a complete entry directory with `entry.env`, the initial archive, and the source package for a full technical test. The entrant instructions define the file roles, literal argument files, qualification OS and offline build. A source-only run still rebuilds, compresses and verifies a fresh decode and is reported as `SOURCE_ONLY_PASS`. A compression-only run leaves archive qualification pending. The full workflow also tests the submitted archive. Preserve the commit, toolchain and host configuration, artifact hashes, score components and per-phase time, memory and disk evidence. Human judges decide eligibility and the award. [Verifier workflow](https://github.com/jabowery/HutterPrizeJudgingAssistant/blob/4f4a9a1a14abdbae6522ab06b4b898cfdfd0071b/README.md) · [Entrant packaging instructions](https://github.com/jabowery/HutterPrizeJudgingAssistant/blob/4f4a9a1a14abdbae6522ab06b4b898cfdfd0071b/ENTRANT_INSTRUCTIONS.md)

If 93,388,956 becomes that record, a candidate needs **at most 92,455,066 bytes**, a reduction of at least **933,890 bytes**. The award formula is `€500,000 × (L − S) / L`. Processing follows submission time. A failed entry leaves the record in force. ## Submission and attribution

Publish the exact submitted version, options, runnable artifacts, documented source under an OSI-approved license, build and run instructions, an algorithm description, and links for independent testing. Keep upstream notices, attribution, changes and component-specific licenses. The inherited combined project specifies GPL-3.0-only, with separately licensed third-party components and Wikipedia excerpts. For jointly authored submissions, settle the prize split and include it with the entry. [Participation and award terms](https://www.hutter1.net/prize/hrules.htm) · [Upstream license statement](https://github.com/marwoelk/cmix-neif-2.0#9-license) · [Attribution](https://github.com/marwoelk/cmix-neif-2.0/blob/main/NOTICE.md)

Send the numbered information in the participation rules to all three listed committee members. Include a direct archive link, one-line extraction instruction, versions and options, exact artifact sizes, phase timing and peak resources, machine/OS/Geekbench details, and links to the documentation and source. Only the submitted configuration is eligible. Public comment and verification last at least 30 days. A same-author improvement within 30 days can supersede the earlier entry under the published rules. Recheck the queue and rules at submission time. [Submission instructions and award procedure](https://www.hutter1.net/prize/hrules.htm)
